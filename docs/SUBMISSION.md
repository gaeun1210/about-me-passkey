# 과제 8 제출문 — 내 소개 페이지에 패스키 달기

> ✏️ 표시가 있는 곳만 직접 채우면 됩니다. 나머지는 실제 코드와 맞춰 미리 적어 두었습니다.

- **결과물 주소**: ✏️ https://about-me-passkey.vercel.app (Vercel에서 받은 실제 주소로 바꾸기)
- **소스 주소**: https://github.com/gaeun1210/about-me-passkey
- 비공개 공간의 내용은 이 과제를 위해 **만들어 넣은 메모**입니다(owner: 느린 우체국 앱 아이디어, 공개된 채용 정보를 보고 적은 지원 희망 목록, 과제 회고 / guest: 감사 한 줄). 실제 연락처·신분증 번호 같은 개인정보는 없고, 실제 지원 내역도 아닙니다. 계정 이름도 별명(owner, guest)을 썼습니다. 저장소 접속 정보(비밀값)는 Vercel 환경변수에만 있고 소스·제출문 어디에도 없습니다.

---

## 짧은 확인 방법

1. **어디로 가나요** — 결과물 주소를 새 시크릿 창으로 엽니다. 첫 화면이 과제 1 소개 페이지입니다.
2. **세 단계 안에 무엇을 하나요** — ① 소개 내용(01~04)이 보이는지 확인 → ② 위 메뉴의 "🔒 나만의 공간"을 누름 → ③ 아래 "검증 도구"를 펼쳐 "① 로그인 없이 비공개 자료 요청"의 실행을 누름
3. **무엇이 보이면 통과인가요** — 주황 점선 경계선 아래에 "잠겨 있어요" 상자만 보이고 비공개 내용은 없으며, 기록에 `401`과 "패스키로 먼저 들어와야 합니다"가 찍힙니다.
4. **안 될 때는 무엇이 보이나요** — 저장소가 연결되지 않았으면 "준비 중 · 저장소가 연결되지 않았습니다" 상자가, https가 아니거나 패스키를 지원하지 않는 브라우저면 그 이유를 적은 안내 문구가 나옵니다.

## 인증 구현 설명서

### ① 무엇으로 붙였나

- **라이브러리 — `@simplewebauthn/server` (v13)**: 등록 응답 확인, 로그인 서명 확인, 질문 생성을 맡깁니다. 직접 쓴 코드는 그 앞뒤(질문 보관·삭제, 공개키 저장, 세션)뿐입니다.
- 서버: Vercel 서버 함수 (`api/` 폴더)
- 저장소: Upstash Redis (Vercel Storage 연동)
- 로그인 뒤 사람을 알아보는 방법: **세션** — 서버가 32바이트 무작위 세션 번호를 만들어 Redis에 2시간 보관하고, 브라우저에는 `__Host-sid` 쿠키(`HttpOnly; Secure; SameSite=Strict`)로 줍니다. 토큰(JWT)은 쓰지 않았습니다.

### ② 왜 그걸 골랐나

- **라이브러리**: 패스키 확인은 확인할 항목(질문, 사이트 주소, 사이트 ID 해시, 지문·PIN 여부, 서명, 서명 횟수 등)이 많아서 하나라도 빠뜨리면 그대로 취약점이 됩니다. 보안 과제인 만큼, 많은 서비스가 쓰고 검토한 라이브러리에 맡기는 것이 직접 만드는 것보다 안전하다고 판단했습니다.
- **세션 쿠키**: 로그아웃하면 서버에서 세션을 지워 그 값이 바로 무효가 됩니다(토큰은 만료 전까지 살아 있음). HttpOnly라 페이지 스크립트가 값을 읽을 수 없고, `__Host-` 이름이라 다른 하위 도메인이 덮어쓸 수 없습니다.
- **Redis**: 질문을 "2분 뒤 자동 삭제"(`EX 120`)하고 "꺼내면서 지우기"(`GETDEL`)를 명령 하나로 할 수 있어, 질문을 정확히 한 번만 쓰게 만들기 쉽습니다.

그 밖에 더 막아 둔 것:
- 지문·얼굴·PIN 확인 **필수** (`userVerification: required`) — 기기를 주운 사람이 터치만으로 들어올 수 없음
- 패스키를 지우면 **그 계정의 다른 세션을 모두 끊음** — 잃어버린 기기에 열려 있던 화면도 바로 닫힘
- 로그인할 때마다 **세션 번호를 새로 발급**하고 이전 것은 지움 (세션 고정 공격 방지)
- **요청 횟수 제한** — 질문 발급·로그인 확인을 IP마다 10분에 20~30번으로 제한 (IP는 해시로만 저장)
- **계정 수 제한** — 계정은 2개(owner, guest)까지. 두 계정을 만든 뒤에는 새 가입이 자동으로 닫힘
- 운영 주소에서는 사이트 주소를 요청 헤더가 아닌 **Vercel 운영 주소로 고정**
- 상태를 바꾸는 요청은 **같은 사이트에서 온 JSON 요청만** 받음 (다른 사이트·출처 없는 요청 403)
- **보안 헤더**(`vercel.json`): 스크립트는 이 사이트 것만 실행(CSP), 다른 사이트 안에 넣기 금지, HTTPS 강제(HSTS)
- 화면에 그리는 글은 모두 `textContent`로 넣어 스크립트로 실행되지 않음

### ③ 어디를 어떻게 고쳤나

과제 1의 `index.html`은 공개 내용(01~04)을 한 글자도 바꾸지 않았습니다. 바꾼 곳은 메뉴 링크 1개, `private.css`·`private.js` 연결 2줄, 그리고 맨 아래에 붙인 경계선과 **빈** 비공개 자리(`<div id="pv-app">`)뿐입니다. 저장소 커밋 기록 앞부분이 과제 1 기록 그대로라서 무엇을 더했는지 비교할 수 있습니다.

| 흐름 | 지나는 자리 |
|---|---|
| 등록 | `api/register-options.js` L39 질문 생성 → L40 2분 보관 → `private.js` `register()`에서 `navigator.credentials.create()` → `api/register-verify.js` L17 질문 꺼내며 삭제 → L23 `checkRegistration()`(`lib/passkey.js` L31, 라이브러리 확인) → L62 **공개키 저장** / 취소 시 `api/register-cancel.js` |
| 로그인 | `api/login-options.js` L11 질문 생성·보관 → `private.js` `login()`에서 `navigator.credentials.get()` → `api/login-verify.js` L17 질문 꺼내며 삭제 → L24 등록된 패스키인지 → L34 `checkAuthentication()`(`lib/passkey.js` L68, 저장된 공개키로 서명 확인) → L41 새 세션 발급(`lib/http.js` L101) |
| 로그아웃 | `api/logout.js` L8 서버 세션 삭제 → L10 쿠키 비우기 |
| 비공개 자료 조회 | `api/private.js` L13 `requireSession()`(`lib/http.js` L92, 없으면 401) → 세션 주인의 자료만 반환 |

거절을 만들어 내는 소스 위치:

- 로그인 안 함 → 401: `lib/http.js` L96
- 다른 계정 항목 읽기·고치기·지우기 → 403: `api/private.js` L24, L56, L70
- 주소·본문의 다른 계정 이름 무시: `api/private.js` L32, L48 (누구의 자료인지는 세션으로만 정함)
- 다른 계정 패스키 지우기 → 403: `api/passkeys.js` L48
- 이미 쓴 질문 → 401: `api/login-verify.js` L19
- 틀린 서명 → 401: `lib/passkey.js` L81
- 지운 패스키 → 401: `api/login-verify.js` L24
- 마지막 패스키 지우기 → 409: `api/passkeys.js` L52
- 다른 사이트·출처 없는 요청 → 403: `lib/http.js` L51–52

### ④ 안 열리는 것을 확인한 기록

> ✏️ 배포한 사이트의 "검증 도구"에서 버튼을 누르고 **기록 복사**로 붙여 넣습니다. 세션 쿠키 값은 기록에 `sid=●●●●●●(가림)`으로만 남고, 세션은 해시 지문(`fp-…`)으로만 보입니다.

**패스키를 저장한 곳** ✏️ (패스키 목록의 "저장 위치(추정)"을 보고 적기)
- 계정 owner의 패스키 1: ✏️ 예) 노트북 Windows Hello — 기기 자체
- 계정 owner의 패스키 2: ✏️ 예) 휴대폰 — 구글 비밀번호 관리자
- 계정 guest의 패스키: ✏️

**서버에 저장된 값** ✏️ (패스키 목록 → "서버에 저장된 값 보기" 또는 검증 도구 ⑨)
```
✏️ -----BEGIN PUBLIC KEY----- … -----END PUBLIC KEY-----
```
이 값은 **공개키**입니다. 비밀번호가 아닙니다. 공개키로는 서명이 맞는지 "확인"만 할 수 있고 서명을 "만들" 수는 없어서, 이 값이 유출되어도 이것만으로는 들어올 수 없습니다. 개인키는 기기 밖으로 나오지 않습니다.

**등록 요청 본문** — 개인키가 가지 않는다는 기록 ✏️ (기록 중 "등록 2단계 — 공개키 보내기")
요청 본문에는 `clientDataJSON`, `attestationObject`, `transports`만 있고, 기록의 메모에 "개인키(private key) 항목: 없음"이 함께 찍힙니다.

**질문 값이 매번 다르다는 기록** ✏️ (들어온 상태에서 검증 도구 ③ — 등록용 3개, 로그인용 3개)

**등록 취소** ✏️ (패스키 창에서 취소 → "등록 취소 — 보관하던 질문 지우기" 기록과 화면 안내)

| 확인 | 통과한 요청 | 거절된 요청 |
|---|---|---|
| 로그인 없이 열기 | ✏️ 들어온 뒤 "비공개 자료 조회" 200 | ✏️ 검증 ① 401 / 검증 ② 첫 화면 HTML에 비공개 문구 0건 |
| 남의 패스키로 열기 | ✏️ owner로 내 자료 조회 200, `?owner=guest` 붙여도 owner 자료만 200 (검증 ⑧) | ✏️ owner가 guest 항목 읽기·지우기 403, guest가 owner 항목 읽기 403 (검증 ⑦ 양방향) |
| 이미 쓴 질문 재사용 | ✏️ "로그인 2단계 — 서명 보내기" 200 | ✏️ 검증 ④ 같은 본문 다시 보내기 401 `CHALLENGE_UNKNOWN` |
| 패스키 삭제 뒤 로그인 | ✏️ 남은 패스키로 로그인 200 | ✏️ 지운 패스키로 로그인 401 `UNKNOWN_PASSKEY` |

추가 기록 ✏️
- 서명 확인 성공과 실패를 나란히: 정상 로그인 200 ↔ 검증 ⑤ 서명 1바이트 바꾸기 401 `BAD_SIGNATURE`
- 로그아웃 뒤 같은 세션 값으로 요청: 검증 ⑥ 401 ("보낸 세션(fp-…)은 로그아웃했거나 만료")
- 거절 앞뒤로 상대편 자료 건수가 같음: guest로 검증 ⑨ "내 자료 건수" → owner로 검증 ⑦ 지우기 시도 403 → 다시 guest로 ⑨, 건수 같음
- 패스키가 하나도 남지 않을 때: 마지막 패스키 지우기를 누르면 409와 함께 "지우면 이 계정에 다시 들어갈 방법이 없어 막아 두었다"는 안내가 화면에 나옵니다. 마지막 하나는 서버가 지우지 않으므로 계정이 열쇠 없이 남는 일은 없습니다. 다만 그 기기를 잃어버리면 복구할 방법은 없습니다(⑥ 참고).

### ⑤ AI와 나

> ✏️ 직접 겪은 대로 고쳐 쓰세요. 아래는 출발점입니다.

- **AI에게 맡긴 일**: 서버 코드(등록·로그인·로그아웃·비공개 자료·패스키 목록), 화면과 검증 도구, 가상 인증기로 하는 자동 테스트, 이 설명서의 초안
- **내가 직접 판단한 일**: ✏️ 예) 과제 1 주소를 덮지 않고 새 저장소 `about-me-passkey`로 진행 / 보안 과제이므로 취약점을 최대한 줄이는 쪽을 우선함 / 비공개 항목 주제와 내용(느린 우체국 앱 아이디어, 지원해 보고 싶은 곳, 과제 회고, guest의 감사 한 줄) / 패스키 두 개를 어느 기기에 둘지 / 실제 기기에서 확인하고 기록을 고름
- **AI 말을 따르지 않은 일**: ✏️ 예) AI는 이미 테스트가 끝난 직접 구현 코드를 그대로 쓰자고 추천했지만, 보안 과제인 만큼 검증된 라이브러리가 더 안전하다고 판단해 라이브러리로 바꾸고 약점도 더 막게 함

### ⑥ 아직 못 막은 것

1. **모든 패스키 기기를 잃어버리면 복구할 방법이 없습니다.** 마지막 패스키 삭제는 막았지만, 두 기기를 모두 잃어버리거나 초기화하는 일은 막을 수 없고, 이메일 같은 다른 복구 수단도 없습니다.
2. **배포 직후 누군가 먼저 계정을 만들면 자리를 뺏길 수 있습니다.** 계정 수를 2개로 제한해 그 뒤의 가입은 막았지만, 배포한 순간부터 두 계정을 만들기 전까지는 누구나 가입할 수 있습니다. (배포 직후 바로 owner·guest를 만들어 이 시간을 줄였습니다.)
3. **요청 횟수 제한은 IP 기준이라 우회할 수 있습니다.** IP를 여러 개 쓰는 공격자는 제한을 피해 질문 발급을 많이 할 수 있습니다. 질문은 2분 뒤 지워지지만 발급 자체를 완전히 막지는 못합니다.
4. **인증기 증명(attestation)을 확인하지 않습니다.** 어떤 회사의 어떤 인증기인지 서버가 검증하지 않아서, 목록의 "저장 위치"는 AAGUID 번호로 짐작한 값입니다.
5. **기기 자체가 악성 프로그램에 감염되면 막을 수 없습니다.** 세션 쿠키는 HttpOnly라 페이지 스크립트는 못 읽지만, 기기 안의 악성 프로그램이 쿠키를 훔치면 세션이 끝날 때(최대 2시간)까지 쓸 수 있습니다.
6. **라이브러리 버전을 잠그지 않았습니다.** `^13.0.0`이라 배포할 때마다 13.x의 최신판을 받습니다. 보안 수정은 자동으로 들어오지만, 그 버전에 문제가 생기면 그대로 받게 됩니다.
