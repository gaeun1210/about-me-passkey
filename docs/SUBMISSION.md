# 과제 8 제출문 — 내 소개 페이지에 패스키 달기

> ✏️ 표시가 있는 곳만 직접 채우면 됩니다. 나머지는 실제 코드와 맞춰 미리 적어 두었습니다.

- **결과물 주소**: ✏️ https://about-me-passkey.vercel.app (Vercel에서 받은 실제 주소로 바꾸기)
- **소스 주소**: https://github.com/gaeun1210/about-me-passkey
- 비공개 공간에 들어 있는 내용은 모두 **만들어 넣은 예시**이며, 실제 연락처·신분증 번호 같은 개인정보는 없습니다. 계정 이름도 별명(예: owner, guest)을 썼습니다. 저장소 접속 정보(비밀값)는 Vercel 환경변수에만 있고 소스·제출문 어디에도 없습니다.

---

## 짧은 확인 방법

1. **어디로 가나요** — 결과물 주소를 새 시크릿 창으로 엽니다. 첫 화면이 과제 1 소개 페이지입니다.
2. **세 단계 안에 무엇을 하나요** — ① 소개 내용(01~04)이 보이는지 확인 → ② 위 메뉴의 "🔒 나만의 공간"을 누름 → ③ 아래 "검증 도구"를 펼쳐 "① 로그인 없이 비공개 자료 요청"의 실행을 누름
3. **무엇이 보이면 통과인가요** — 주황 점선 경계선 아래에 "잠겨 있어요" 상자만 보이고 비공개 내용은 없으며, 기록에 `401`과 "패스키로 먼저 들어와야 합니다"가 찍힙니다.
4. **안 될 때는 무엇이 보이나요** — 저장소가 연결되지 않았으면 "준비 중 · 저장소가 연결되지 않았습니다" 상자가, https가 아니거나 패스키를 지원하지 않는 브라우저면 그 이유를 적은 안내 문구가 나옵니다.

## 인증 구현 설명서

### ① 무엇으로 붙였나

- **직접 구현** — 표준 WebAuthn(패스키) 흐름을 Node.js 내장 `crypto` 모듈로 직접 확인합니다. 외부 인증 서비스나 패스키 라이브러리는 쓰지 않았습니다.
  - 서명 확인: `crypto.verify` (ES256 · EdDSA · RS256)
  - 패스키 응답 해석: 직접 만든 작은 CBOR 해석기 (`lib/cbor.js`)
- 서버: Vercel 서버 함수 (`api/` 폴더)
- 저장소: Upstash Redis (Vercel Storage 연동, REST로 호출)
- 로그인 뒤 사람을 알아보는 방법: **세션** — 서버가 32바이트 무작위 세션 번호를 만들어 Redis에 8시간 보관하고, 브라우저에는 `HttpOnly; Secure; SameSite=Strict` 쿠키(`sid`)로 줍니다. 토큰(JWT)은 쓰지 않았습니다.

### ② 왜 그걸 골랐나

- 처음에는 널리 쓰이는 SimpleWebAuthn 라이브러리를 쓰려 했지만, 작업 환경에서 npm 패키지를 받을 수 없어 라이브러리 없이 직접 확인 코드를 만들었습니다. 대신 서명 확인 자체는 직접 만들지 않고 Node가 제공하는 검증된 `crypto.verify`에 맡겼습니다.
- 직접 만든 덕분에 "질문을 꺼내면서 지운다", "저장된 공개키로 서명을 확인한다" 같은 과제의 핵심 단계가 코드 한 줄 한 줄로 드러나 설명서 ③·④와 바로 이어집니다.
- 세션 쿠키를 고른 이유: 로그아웃하면 서버에서 세션을 지워 그 값이 바로 무효가 되고(토큰은 만료 전까지 살아 있음), HttpOnly라 페이지 스크립트가 값을 읽을 수 없기 때문입니다.
- Redis를 고른 이유: 질문을 "5분 뒤 자동 삭제"하는 설정(`EX 300`)과 "꺼내면서 지우기"(`GETDEL`)가 명령 하나로 되기 때문입니다.

### ③ 어디를 어떻게 고쳤나

과제 1의 `index.html`은 공개 내용(01~04)을 한 글자도 바꾸지 않았습니다. 바꾼 곳은 메뉴 링크 1개, `private.css`·`private.js` 연결 2줄, 그리고 맨 아래에 붙인 경계선과 **빈** 비공개 자리(`<div id="pv-app">`)뿐입니다. 저장소 커밋 기록 앞부분이 과제 1 기록 그대로라서 무엇을 더했는지 비교할 수 있습니다.

| 흐름 | 지나는 자리 |
|---|---|
| 등록 | `api/register-options.js` L34–39 질문 생성·5분 보관 → `private.js` `register()`에서 `navigator.credentials.create()` → `api/register-verify.js` L15 질문 꺼내며 삭제 → L21 `verifyRegistration()`(`lib/webauthn.js` L109) → L55 **공개키 저장** / 취소 시 `api/register-cancel.js` |
| 로그인 | `api/login-options.js` 질문 생성 → `private.js` `login()`에서 `navigator.credentials.get()` → `api/login-verify.js` L13 질문 꺼내며 삭제 → L20 등록된 패스키인지 → L23 `verifyAuthentication()`(`lib/webauthn.js` L164 서명 확인) → L36 세션 발급(`lib/http.js` L80) |
| 로그아웃 | `api/logout.js` L9 서버 세션 삭제 → L11 쿠키 비우기 |
| 비공개 자료 조회 | `api/private.js` L12 `requireSession()`(`lib/http.js` L71, 없으면 401) → 세션 주인의 자료만 반환 |

거절을 만들어 내는 소스 위치:

- 로그인 안 함 → 401: `lib/http.js` L75
- 다른 계정 항목 읽기·지우기 → 403: `api/private.js` L23, L54
- 주소·본문의 다른 계정 이름 무시: `api/private.js` L30, L46 (누구의 자료인지는 세션으로만 정함)
- 다른 계정 패스키 지우기 → 403: `api/passkeys.js` L50
- 이미 쓴 질문 → 401: `api/login-verify.js` L15
- 틀린 서명 → 401: `lib/webauthn.js` L164
- 지운 패스키 → 401: `api/login-verify.js` L20
- 마지막 패스키 지우기 → 409: `api/passkeys.js` L54

### ④ 안 열리는 것을 확인한 기록

> ✏️ 배포한 사이트의 "검증 도구"에서 버튼을 누르고 **기록 복사**로 붙여 넣습니다. 세션 쿠키 값은 기록에 `sid=●●●●●●(가림)`으로만 남고, 세션은 해시 지문(`fp-…`)으로만 보입니다.

**패스키를 저장한 곳** ✏️ (패스키 목록의 "저장 위치(추정)"을 보고 적기)
- 계정 owner의 패스키 1: ✏️ 예) 노트북 Windows Hello — 기기 자체
- 계정 owner의 패스키 2: ✏️ 예) 휴대폰 — 구글 비밀번호 관리자
- 계정 guest의 패스키: ✏️

**서버에 저장된 값** ✏️ (패스키 목록 → "서버에 저장된 값 보기" 또는 검증 도구 ⑨)
```
✏️ -----BEGIN PUBLIC KEY----- … -----END PUBLIC KEY-----
```
이 값은 **공개키**입니다. 비밀번호가 아닙니다. 공개키로는 서명이 맞는지 "확인"만 할 수 있고 서명을 "만들" 수는 없어서, 이 값이 유출되어도 이것만으로는 들어올 수 없습니다. 개인키는 기기 밖으로 나오지 않습니다.

**등록 요청 본문** — 개인키가 가지 않는다는 기록 ✏️ (기록 중 "등록 2단계 — 공개키 보내기")
요청 본문에는 `clientDataJSON`, `attestationObject`, `transports`만 있고, 기록의 메모에 "개인키(private key) 항목: 없음"이 함께 찍힙니다.

**질문 값이 매번 다르다는 기록** ✏️ (검증 도구 ③ — 등록용 3개, 로그인용 3개)

**등록 취소** ✏️ (패스키 창에서 취소 → "등록 취소 — 보관하던 질문 지우기" 기록과 화면 안내)

| 확인 | 통과한 요청 | 거절된 요청 |
|---|---|---|
| 로그인 없이 열기 | ✏️ 들어온 뒤 "비공개 자료 조회" 200 | ✏️ 검증 ① 401 / 검증 ② 첫 화면 HTML에 비공개 문구 0건 |
| 남의 패스키로 열기 | ✏️ owner로 내 자료 조회 200, `?owner=guest` 붙여도 owner 자료만 200 (검증 ⑧) | ✏️ owner가 guest 항목 읽기·지우기 403, guest가 owner 항목 읽기 403 (검증 ⑦ 양방향) |
| 이미 쓴 질문 재사용 | ✏️ "로그인 2단계 — 서명 보내기" 200 | ✏️ 검증 ④ 같은 본문 다시 보내기 401 `CHALLENGE_UNKNOWN` |
| 패스키 삭제 뒤 로그인 | ✏️ 남은 패스키로 로그인 200 | ✏️ 지운 패스키로 로그인 401 `UNKNOWN_PASSKEY` |

추가 기록 ✏️
- 서명 확인 성공과 실패를 나란히: 정상 로그인 200 ↔ 검증 ⑤ 서명 1바이트 바꾸기 401 `BAD_SIGNATURE`
- 로그아웃 뒤 같은 세션 값으로 요청: 검증 ⑥ 401 ("보낸 세션(fp-…)은 로그아웃했거나 만료")
- 거절 앞뒤로 상대편 자료 건수가 같음: guest로 검증 ⑨ "내 자료 건수" → owner로 검증 ⑦ 지우기 시도 403 → 다시 guest로 ⑨, 건수 같음
- 패스키가 하나도 남지 않을 때: 마지막 패스키 지우기를 누르면 409와 함께 "지우면 이 계정에 다시 들어갈 방법이 없어 막아 두었다"는 안내가 화면에 나옵니다. 마지막 하나는 서버가 지우지 않으므로 계정이 열쇠 없이 남는 일은 없습니다. 다만 그 기기를 잃어버리면 복구할 방법은 없습니다(⑥ 참고).

### ⑤ AI와 나

> ✏️ 직접 겪은 대로 고쳐 쓰세요. 아래는 출발점입니다.

- **AI에게 맡긴 일**: 서버 코드(등록·로그인·로그아웃·비공개 자료·패스키 목록), 패스키 응답 해석과 서명 확인 코드, 화면과 검증 도구, 가상 인증기로 하는 자동 테스트, 이 설명서의 초안
- **내가 직접 판단한 일**: ✏️ 예) 과제 1 주소를 덮지 않고 새 저장소 `about-me-passkey`로 진행 / 저장소 이름을 영어로 정함 / 비공개 항목 내용 / 패스키 두 개를 어느 기기에 둘지 / 실제 기기에서 확인하고 기록을 고름
- **AI 말을 따르지 않은 일**: ✏️ 예) AI는 처음에 과제 1 저장소에 그대로 붙이자고 했지만, 과제 1 제출본을 보존하려고 새 저장소로 바꿈 (없다면 왜 없었는지)

### ⑥ 아직 못 막은 것

1. **패스키를 지워도 이미 만들어진 세션은 남습니다.** 잃어버린 기기의 패스키를 목록에서 지워도, 그 기기에 이미 열려 있는 세션은 최대 8시간 동안 계속 쓸 수 있습니다. 패스키 삭제 때 그 계정의 다른 세션을 모두 끊는 기능이 없습니다.
2. **누구나 계정을 만들 수 있고, 요청 횟수 제한이 없습니다.** 계정끼리 자료는 섞이지 않지만, 누군가 계정이나 질문 발급 요청을 대량으로 만들어 저장소를 채울 수 있습니다. 질문은 5분 뒤 지워지지만 발급 자체를 막지는 못합니다.
3. **모든 패스키 기기를 잃어버리면 복구할 방법이 없습니다.** 마지막 패스키 삭제는 막았지만, 기기 분실·초기화는 막을 수 없고 이메일 같은 복구 수단도 없습니다.
4. **인증기 증명(attestation)을 확인하지 않습니다.** 어떤 회사의 어떤 인증기인지 서버가 검증하지 않아서, 목록의 "저장 위치"는 AAGUID 번호로 짐작한 값입니다.
5. **지문·PIN 확인을 필수로 요구하지 않습니다**(`userVerification: preferred`). 보안 키처럼 터치만 하는 인증기로도 통과할 수 있습니다.
6. **확인 코드를 직접 만들었습니다.** 서명 확인은 Node `crypto`에 맡겼지만, 응답 해석과 확인 순서는 많은 사람이 검토한 라이브러리가 아니라 이번에 만든 코드입니다.
